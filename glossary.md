**Core Objects**
- Symmetry: a named change-of-basis or permutation degree of freedom that can act on one tensor axis across one or more ParameterComponents. In code, each symmetry is keyed by name inside `Symmeters`, and transforms are applied by matching that name against ParameterComponent axes. A symmetry may use either one shared square matrix or a bank of square matrices indexed by another axis such as `L0.head`. Example: `L0.qk` is the query/key symmetry family for layer 0, and it can apply a different qk transform to each head.
- Symmeters: the project’s main serialized parameter container. It is a dict-like object mapping `symmetry_name -> {component_name -> ParameterComponent}`. Conceptually, it is “all model parameters, reorganized by symmetry structure instead of by module tree.” Example: after serializing a tiny BERT, `symmeters` may have keys like `model`, `L0.qk`, `L0.ov`, `L0.mlp`, and `L0.head`.
- ParameterComponent: one named structured parameter payload inside a symmetry. A ParameterComponent usually corresponds to one semantically meaningful parameter group such as `query.weight`, `query.bias`, an embedding table, or a LayerNorm pair. ParameterComponents are added with `add_component(...)`. Example: `bert.encoder.layer.0.attention.self.query.weight` is one ParameterComponent inside `L0.qk`.
- ParameterComponent class: the structured object that describes one ParameterComponent. It carries `tensor`, `axes`, `kind`, `layout`, and `parameter_keys`. Example: a query-weight ParameterComponent says the stored tensor has axes `(L0.head, L0.qk, model)` and layout `head_rows`.
- Block: a design-note term for a semantically meaningful chunk of parameters that should stay together during canonicalization. The notes talk about block-structured symmetries with shape `(num_blocks, known_dim, unknown_dim)`, but the current implementation does not have a `Block` class; instead, the practical unit in code is a ParameterComponent plus its axis metadata. Example: the design note treats `[query, key]` as the `qk` blocks for one attention substructure.
- Serialized model: a model converted into `Symmeters` form by `serialize_model(...)`, so its parameters can be transformed, canonicalized, or reloaded via overrides. Example: `serialize_model(model)` turns ordinary HF weights into symmetry-tagged ParameterComponents that can be permuted and then loaded back without changing outputs.

**Structure Terms**
- Axis: a named semantic dimension of a ParameterComponent tensor, stored in `component.axes`. Examples are `model`, `L0.qk`, `L0.head`, `vocab_items`, or `layernorm_param`. A symmetry acts wherever its name appears in a ParameterComponent’s axes tuple. Example: if a ParameterComponent has axes `(L0.head, L0.qk, model)`, then head permutations act on axis 0, qk transforms on axis 1, and model transforms on axis 2.
- Owned ParameterComponents: the ParameterComponents stored under a given symmetry key. `owned_components(symmetry_name)` means “ParameterComponents this symmetry owns directly,” as opposed to all ParameterComponents that merely contain that axis. Example: `owned_components("L0.qk")` returns the query/key ParameterComponents stored under `L0.qk`, but not a `model`-owned output bias.
- ParameterComponents with axis: all ParameterComponents anywhere in `Symmeters` whose tensor includes a given axis name. This is broader than ownership and is what transformation code uses to find every affected tensor. Example: asking for ParameterComponents with axis `L0.head` finds query, key, value, and output-slice ParameterComponents because all of them expose a head axis.
- Symmetry size: the size of the tensor dimension associated with a symmetry, inferred from all ParameterComponents carrying that axis. The code checks that every occurrence agrees. Example: if every `L0.head` axis has length 12, then `symmetry_size("L0.head")` is 12.
- Ordered transform names: the canonical order in which transforms are expected to be applied: `model`, `decoder`, then per-layer `qk`, `ov`, `mlp`, `head`, then anything else except `vocab`. Example: on an untied one-layer model the order might be `model`, `decoder`, `L0.qk`, `L0.ov`, `L0.mlp`, `L0.head`. For `qk` and `ov`, one ordered name still represents a whole bank of per-head transforms rather than only one shared matrix.
- Transform bank axis: an axis that indexes a bank of transforms for another symmetry. In the current code, `L{i}.head` is the bank axis for both `L{i}.qk` and `L{i}.ov`, which means each head can get its own qk or ov transform while still sharing the same serializer layout. Example: `L0.qk` uses `L0.head` as its bank axis, so layer 0 can learn 12 different qk permutations, one per head.

**Model-Specific Symmetry Names**
- `model`: the hidden-state symmetry. This is the main residual/hidden basis being canonicalized across embeddings, output biases, LayerNorms, and other hidden-dimension-owned parameters. It is the central symmetry in the system. Example: the word embedding matrix is stored with axes `(vocab_items, model)`, so the model symmetry acts on its hidden dimension.
- `decoder`: the MLM-head hidden symmetry used when input embeddings and output embeddings are untied. If embeddings are tied, this symmetry does not exist separately and the transform lives under `model`. Example: when the decoder weight is separate from the input embedding matrix, `cls.predictions.decoder.weight` lives under `decoder` rather than `model`.
- `vocab`: the vocabulary-axis symmetry, currently used for the decoder bias ParameterComponent rather than for hidden-state canonicalization. It is intentionally excluded from `ordered_transform_names()`. Example: `cls.predictions.decoder.bias` is stored with axes `(vocab,)`.
- `L{i}.qk`: the per-layer attention query/key symmetry family. It governs the per-head hidden dimension shared by query and key projections, but the actual transform is banked by `L{i}.head`, so head 3 and head 7 can canonicalize differently. Example: both `...self.query.weight` and `...self.key.weight` in layer 0 are ParameterComponents under `L0.qk`, and the test suite can apply 12 distinct qk permutations inside that one symmetry family.
- `L{i}.ov`: the per-layer attention value/output symmetry family. It governs the per-head hidden dimension shared by value and attention-output slices, and like `qk` it now uses a per-head bank of transforms indexed by `L{i}.head`. Example: `...self.value.weight` and `...output.dense.weight` for layer 0 are ParameterComponents under `L0.ov`, but each head’s ov basis can be permuted independently.
- `L{i}.mlp`: the per-layer feedforward symmetry. It governs the intermediate MLP width connecting the layer’s up-projection and down-projection. Example: the intermediate dense weight and the transposed output dense weight for layer 0 both live under `L0.mlp`.
- `L{i}.head`: the per-layer attention-head axis. This is the symmetry that permutes heads as units. It is separate from `qk` and `ov`, which act within each head, and it also serves as the bank axis that indexes the per-head `qk` and `ov` transforms. Example: swapping heads 3 and 7 in layer 0 is an `L0.head` transform, while changing only head 3’s qk basis is part of the banked `L0.qk` transform.

**ParameterComponent Metadata**
- `tensor`: the actual stored parameter tensor for a ParameterComponent. It may be a raw parameter, a transposed parameter, a head-stacked parameter, or a stacked LayerNorm tensor depending on layout. Example: a query weight that is originally shape `(768, 768)` might be stored as `(12, 64, 768)` after head stacking.
- `axes`: the semantic names of each tensor dimension. This is how the project knows which transforms apply where. Example: the axes `(L0.head, L0.ov, model)` mean head transport acts on the first dimension and model-space transport acts on the last.
- `kind`: a coarse semantic tag like `weight`, `bias`, or `layernorm`. It is descriptive metadata; most transform logic keys off `axes` and `layout`, not `kind`. Example: `query.bias` has kind `bias`, while `query.weight` has kind `weight`.
- `layout`: the codec rule for converting between the stored ParameterComponent tensor and one or more real model parameters. Layout is what makes save/load work. Example: an output projection weight uses a transposed head-stacked layout so it can share the same explicit head axis convention as value weights.
- `parameter_keys`: the original state-dict keys that this ParameterComponent corresponds to when rebuilding model overrides. A ParameterComponent can map to one parameter or several, such as a LayerNorm weight/bias pair. Example: a LayerNorm ParameterComponent maps to both `...LayerNorm.weight` and `...LayerNorm.bias`.

**Layout Names**
- `identity`: store the tensor in the same orientation as the target parameter. Reloading is just `parameter = tensor`. Example: the embedding matrix is stored as-is with shape `(vocab_size, hidden_size)`.
- `transpose`: store a tensor transposed relative to the target parameter, then transpose it back on load. Used for some output-side matrices so the symmetry axis appears in the desired slot. Example: the MLP output dense weight is stored as `weight.T` so the MLP symmetry is the first axis.
- `head_rows`: store an attention weight as `(num_heads, head_dim, model_dim)` so both head identity and within-head symmetry are explicit. Reloading flattens heads back into normal matrix rows. Example: a BERT-base query weight of shape `(768, 768)` becomes `(12, 64, 768)`.
- `head_rows_transposed`: same idea as `head_rows`, but the flattened result is transposed on load. Used for attention output weights. Example: the attention output dense weight is stored as stacked slices of `weight.T` so it aligns with the `ov` symmetry convention.
- `head_bias`: store an attention bias as `(num_heads, head_dim)` so head permutations can act on it naturally. Reloading flattens it back to a 1D bias vector. Example: a 768-wide query bias becomes `(12, 64)`.
- `layernorm`: store LayerNorm as a stacked 2-row tensor `[weight, bias]`. Reloading splits it back into two separate parameters. Example: one ParameterComponent tensor stores both `LayerNorm.weight` and `LayerNorm.bias` together instead of as two unrelated entries.

**Transformation Terms**
- Transform: a square matrix, or a bank of square matrices, applied along every tensor axis named by a given symmetry. In practice this is `apply_transform(symmetry_name, matrix)`. Example: applying a `2 x 2` swap matrix to `L0.qk` swaps the two qk coordinates everywhere, while applying a `(12, 64, 64)` bank to `L0.qk` lets each head use a different qk permutation.
- Head transport: the same idea as a transform, but specialized naming for the `L{i}.head` axis because it usually represents head permutation or soft head matching. In code it is just `apply_transform` routed through `apply_head_transport(...)`. Example: applying a head swap to `L0.head` simultaneously reorders query, key, value, and output slices for layer 0, and also reindexes which per-head qk/ov bank entry belongs to each head.
- Transport matrix: the soft or hard matrix predicted by an aligner and then applied to a symmetry. In this codebase “transport” usually means a Sinkhorn-normalized approximately doubly-stochastic matrix that may later correspond to a permutation. For banked symmetries, the transport can be a stack of matrices rather than just one matrix. Example: a head transport might be close to the identity except for two heads whose mass is mostly swapped, while a qk transport can be a bank of 12 separate near-permutation matrices.
- Permutation invariance: the core property under test that applying consistent symmetry transforms to serialized parameters does not change the function of the model. The tests use random permutation matrices to check this. Example: you can randomly permute every symmetry of a serialized BERT and the reloaded model should still produce the same logits.
- Distinct permutation count: the number of logically separate permutation matrices being exercised in an invariance test. This can be larger than the number of named symmetries when some symmetries are banked. Example: untied BERT-base has 303 distinct permutations in the full test: 1 `model`, 1 `decoder`, 144 `qk`, 144 `ov`, 12 `mlp`, and 1 shared head permutation.

**Canonicalization Terms**
- Canonicalization: the process of choosing a standard basis within each symmetry so different but functionally equivalent parameterizations line up. In practice the `Canonicalizer` predicts transport matrices from symmetry evidence and applies them. Example: two independently trained but equivalent layers may use different internal neuron orderings; canonicalization tries to pick one ordering for both.
- Canonical basis: the chosen reference basis after canonicalization. The notes use this language mainly for hidden space under the `model` symmetry. Example: after canonicalization, the residual-space coordinates of two models are intended to refer to the same hidden directions rather than arbitrary permutations.
- Evidence: the parameter content used to infer a symmetry’s transform. In current code, evidence is built by flattening the owned ParameterComponents of a symmetry along that symmetry axis and concatenating them. For banked symmetries such as `L{i}.qk` and `L{i}.ov`, the head axis is preserved so the aligner can predict one transport per head. Example: for `L0.mlp`, the evidence comes from the intermediate weight, intermediate bias, and output weight ParameterComponents owned by that symmetry.
- Evidence components: the individual flattened ParameterComponent contributions that get concatenated into one evidence tensor for an aligner. For banked symmetries, these contributions are concatenated within each bank entry rather than collapsing the bank axis away. Example: the flattened query-weight ParameterComponent and flattened query-bias ParameterComponent are two separate evidence contributions before concatenation.
- Aligner: a module that predicts a transport matrix from evidence. The current code has `DimensionAligner` for ordinary symmetries and `HeadAligner` for head permutations. Example: the model aligner predicts a hidden-space transport, while the head aligner predicts how to reorder attention heads.
- DimensionAligner: the generic Sinkhorn-based matcher for non-head symmetries. It consumes evidence shaped like `(batch, known_size, unknown_size)` and predicts a transport over the unknown dimension. If the symmetry is banked, the bank dimension is treated like batch, so one call can produce one transport per head. Example: it can predict a bank of transports for `L0.qk` based on the flattened query/key ParameterComponents while preserving the head axis.
- HeadAligner: the aligner for head symmetry. It first encodes per-head descriptors, then runs Sinkhorn on the descriptor similarity matrix. Example: it compares the learned descriptor for head 0 against heads 1 through 11 to decide whether any should swap.
- HeadDescriptorEncoder: the module that converts head-owned ParameterComponent tensors into one compact descriptor vector per head before alignment. Example: it summarizes each head using the query, key, value, and output-slice ParameterComponents instead of flattening the entire per-head parameter bundle directly into Sinkhorn.
- Descriptor: a compressed feature representation of a symmetry’s evidence, especially for head alignment. The design notes use this as the intended interface between symmetry-specific encoders and a generic transport matcher. Example: instead of representing one head by roughly 200k raw numbers, the encoder might reduce it to a 64-dimensional descriptor.
- Active symmetries: the subset of symmetries the canonicalizer should process in a forward pass. If omitted, it canonicalizes all ordered transform names except `model`, while still always requiring `model` to exist. Example: you can ask the canonicalizer to operate only on `("L0.qk",)` if you want to leave `ov`, `mlp`, and head order untouched.

**Model Codec Terms**
- Serialize: convert a Hugging Face MLM model into `Symmeters`. The project has serializer entry points for embeddings, attention, encoder layers, the MLM head, and the full model. Example: `serialize_attention(...)` turns ordinary attention matrices into ParameterComponents with explicit `head`, `qk`, and `ov` axes.
- Load serialized: instantiate a pretrained shell model and build parameter overrides from `Symmeters` so the shell behaves like the serialized parameters. Example: after permuting a serialized model, `load_serialized(...)` rebuilds the matching parameter tensors so the shell still computes the same function.
- Override: a `state_dict`-style parameter replacement produced from ParameterComponents and passed into `functional_call(...)` or otherwise applied to a shell model. Example: one override entry might be `{"bert.encoder.layer.0.attention.self.query.weight": tensor}`.
- Materialize ParameterComponent override: convert one ParameterComponent back into one or more ordinary parameter tensors based on its layout and parameter keys. Example: a `layernorm` ParameterComponent produces two outputs, one for `LayerNorm.weight` and one for `LayerNorm.bias`.
- Shell model: not a formal class name, but the repo uses the standard pattern of loading a pretrained model architecture and then swapping in serialized parameters via overrides. Example: `bert-base-uncased` loaded from Hugging Face becomes the shell, and the serialized ParameterComponents provide the actual weights you want to evaluate.

**Tying Terms**
- Tied embeddings: the MLM decoder weight is the exact same tensor as the input word embeddings. In that case there is no separate `decoder` symmetry; the transform-side dense weight belongs to `model`. Example: changing the input embedding weight also changes the output decoder weight because they are literally the same tensor.
- Untied embeddings: the decoder weight is separate from the input embedding matrix. In that case the repo introduces a distinct `decoder` symmetry to capture the extra hidden-space degree of freedom. Example: you can permute decoder hidden coordinates without simultaneously permuting the input embeddings.

**Math/Planning Terms**
- Known dimension: in the design notes, the left-side dimension shared with the model transform. It is the conditioning dimension used as evidence for predicting the right-side symmetry transform. Example: in a `(known_dim, unknown_dim)` MLP block, the known dimension is the hidden-space side that conditions the prediction of the MLP transport.
- Unknown dimension: in the design notes, the dimension canonicalized by the symmetry-specific right-side transform. In code this becomes the dimension over which `DimensionAligner` predicts transport. Example: for `L0.mlp`, the unknown dimension is the intermediate width being reordered or canonically aligned.
- Sinkhorn: the normalization procedure used to convert logits into an approximately doubly-stochastic transport matrix. It is the core soft matching primitive in canonicalization. Example: if a raw similarity matrix slightly prefers swapping two heads, Sinkhorn turns that into a near-permutation matrix with rows and columns that sum to 1.
- Soft transport: a Sinkhorn output matrix that behaves like a relaxed permutation rather than an exact hard permutation. Example: a row might assign `0.9` mass to one target head and `0.1` to another instead of committing to a single one-hot match.
- Hardened transport: converting a soft transport into an exact permutation for strict evaluation or export. Example: turning a near-swap matrix into an exact head-swap permutation before exporting a model.

**Evaluation / Utility Terms**
- Pseudo-perplexity: the masked-token evaluation metric computed by repeatedly masking one token at a time and exponentiating the mean loss. The helper is `masked_token_pseudo_perplexity(...)`. Example: the code evaluates a sentence by masking each non-special token in turn and averaging the resulting MLM losses.
- Format version 2: the current persisted on-disk format for `Symmeters`. It means the block-native ParameterComponent-based symmetry format; older row-stream formats are intentionally unsupported. Example: a `.pt` file saved today contains a `{"format_version": 2, "symmetries": ...}` payload.

**Historical / Transitional Terms**
- Equivalency prefixes: an older row-era concept for reconstructing semantic groups from parameter name prefixes. The block-native refactor is explicitly meant to eliminate that recovery step. Example: instead of inferring that `query.weight` and `query.bias` belong together because their names share a prefix, the new format stores them as explicit ParameterComponents with explicit axes.
- Block-structured Symmeters: the design direction that moved the repo away from flat row storage and toward ParameterComponents with explicit semantic tensor structure. The current code has implemented the spirit of this, though not as a separate `Block` class. Example: attention weights are now stored as head-stacked ParameterComponents rather than as one large flat matrix with implicit head boundaries.

The shortest way to think about the system is:

- `Symmeters` is the canonical serialized container.
- A `symmetry` is a named transformable axis.
- A `ParameterComponent` is one semantically meaningful tensor payload plus metadata.
- `layout` says how that payload maps back to real model parameters.
- `canonicalization` predicts transport matrices from ParameterComponent evidence and applies them.
